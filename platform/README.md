# Local Workshop

## 일반 채팅과 프로젝트 분석

5293 플랫폼의 **채팅** 메뉴에서 일반 채팅과 프로젝트 분석을 전환할 수 있습니다. 두 모드 모두 에이전트 작업을 만들거나 소스 파일을 수정하지 않습니다. 일반 채팅은 선택한 로컬 모델에 대화만 보냅니다. 프로젝트 분석은 `frontend/src`, `backend/src`와 주요 설정 파일에서 관련 부분을 읽기 전용으로 골라 모델에 전달하고, 답변에 참고 파일을 표시합니다. 검색은 현재 키워드 기반이며 전체 프로젝트를 빠짐없이 읽거나 벡터 검색을 수행하는 기능은 아닙니다.

대화는 프로젝트별로 현재 브라우저 탭의 저장소에 유지되며 **대화 지우기**로 삭제할 수 있습니다. 답변 길이는 1,024·2,048·4,096토큰 중 선택합니다. 로컬 모델 서버가 에이전트 작업에 사용 중일 때는 채팅 전송을 기다리게 하지 않고 사용 중이라고 표시합니다.

## 완료 조건 검증

화면·백엔드 작업은 구현 전에 요청 원문과 항목별 완료 조건을 고정합니다. 기존 빌드·린트·통합 검사와 별개로 `finish` 시점에 계약을 실행합니다. 누락·실패·미확인이 있거나 실제 소스 변경이 없으면 완료 처리하지 않습니다. 관측값과 실패 사유는 모델에 전달합니다.

실행 상세의 **완료 조건** 탭에서 요청별 판정, 검사 조건, 관측값과 계약 해시를 확인합니다. 계약이 없던 예전 실행은 검증 여부를 알 수 없다고 표시합니다.

React 화면 검증은 Playwright로 실제 DOM의 크기·위치·CSS 배치를 관측하고 클릭·입력 후 결과를 확인합니다. React 내부 Fiber API를 사용하지 않습니다. 선택자가 여러 요소에 걸리면 임의의 첫 요소로 통과시키지 않습니다. DOM 관측값과 스크린샷을 저장하며, 화면 전체의 시각적 품질을 보장하는 기능은 아닙니다.

Spring Boot 4 백엔드는 소스를 임시 디렉터리에 복사해 계약에 적힌 MockMvc 요청을 실행합니다. 매번 새 PostgreSQL DB를 만들고 마지막에 삭제합니다. 등록 후 재조회 같은 저장 검사는 계약에 요청 순서와 기대값을 명시합니다. 자동 격리는 현재 Docker 구성(`mdi-db`, `mdi-internal`, `mdi-m2`)을 사용합니다. 지원하지 않는 스택이나 실행할 수 없는 환경은 미확인으로 남깁니다.

일반 브라우저에서는 기본적으로 데이터 변경 요청을 차단합니다. 전체 UI 저장 동작 검증에는 테스트 API를 바라보는 별도 미리보기를 `HARNESS_VERIFICATION_PREVIEW_URL`, `HARNESS_VERIFICATION_BROWSER_ISOLATED=1`로 지정해야 합니다. 일반 미리보기 주소와 같으면 변경을 허용하지 않습니다. 별도 테스트 API 직접 검증에는 `HARNESS_VERIFICATION_API_URL`, `HARNESS_VERIFICATION_API_ISOLATED=1`을 지정합니다. 플랫폼은 프로젝트 미리보기를 읽기 전용 기본 주소로 전달합니다.

최초 계약 생성 후 현재 선택한 모델에 별도 문맥으로 원문과 조건의 일치 여부를 검토시킵니다. 부당한 조건이나 누락이 발견되면 고친 뒤에 계약을 고정합니다. 생성·검토·재작성 외에 항목별 실제 검사에는 모델을 호출하지 않습니다. 검토 모델도 틀릴 수 있으므로 구체화한 기준을 화면에 노출합니다. 지원하지 않는 조건은 수동 확인 항목으로 남기며 자동 성공하지 않습니다. 임의 JavaScript나 셸 명령을 검사 조건으로 받지 않습니다.

계약과 보고서의 기본 저장 경로는 `~/.local/state/local-workshop/verification/<실행 식별자>/`입니다.

Astryx + ECharts로 만든 로컬 개발 플랫폼입니다. 요청 입력, 작업 실행/중지, 실행 기록, 검사 근거, 소스 조회와 앱 미리보기를 한 화면에 모았습니다.

```sh
cd /Users/igkrap/harness101-local
./platform/start.sh
```

화면: http://127.0.0.1:5293 · 앱 개발 서버: http://127.0.0.1:5292

## 프로젝트와 모델

상단 프로젝트 선택 또는 사이드바의 프로젝트 화면에서 전환합니다. 폴더 선택 버튼을 누르면 macOS의 폴더 선택 다이얼로그가 열리고, 선택한 폴더명으로 바로 등록합니다. 취소하면 등록하지 않고, 이미 등록된 폴더를 고르면 해당 프로젝트를 엽니다. 현재 지원하는 프로젝트 구조는 frontend 및 backend 폴더이며, 폴더나 앱 코드를 복사하지 않습니다. 프로젝트 전환은 페이지를 다시 열어 소스 탭과 이전 요청을 섞지 않습니다. 이름과 미리보기 주소를 직접 입력하지 않습니다.

기존 프로젝트 이름도 폴더명으로 맞춥니다. 등록 정보는 `platform/state/projects.json`, 추가 프로젝트의 실행 기록은 `platform/state/projects/<id>/runs/`에 저장합니다. 기존 재고 프로젝트의 실행 기록은 원래 state 위치에 유지합니다. API의 `project` 매개변수로 소스·실행·오류·diff를 구분하며, 다른 프로젝트의 실행 ID는 조회할 수 없습니다. 같은 폴더 또는 상하위 폴더를 중복 등록할 수 없습니다. 모델 작업은 전체 프로젝트에서 한 번에 하나씩 실행합니다.

모델 선택 목록은 프로젝트의 로컬 OpenAI 호환 서버 `/models`에서 읽습니다. 선택한 모델 ID와 서버 주소는 실행 기록에 저장하고 실제 하네스 호출에도 전달합니다. 현재 서버에서 26B MoE와 12B text-only 모델의 응답을 확인했고, 12B의 검색 도구 호출도 확인했습니다. `gemma4_unified_assistant` 형식을 지원하지 않는 모델 하나는 `platform/state/model-health.json`의 실제 호출 실패 근거로 선택을 막았습니다. 런타임을 업데이트해 지원하게 된 경우 이 파일의 해당 항목을 지우면 다시 선택할 수 있습니다. 원격 모델 서버는 현재 허용하지 않습니다.

프로젝트의 실행 설정에서 PostgreSQL 테스트 DB URL을 지정하면 백엔드 검사를 사용할 수 있습니다. 기존 프로젝트와 같은 테스트 DB를 재사용할 수 없습니다. DB 생성과 의존성 설치는 등록 과정에서 수행하지 않습니다. 프로젝트에 전용 harness가 없으면 기존 로컬 모델 하네스를 공용 실행기로 사용합니다.

## 자동 미리보기

미리보기 탭을 열면 해당 frontend 폴더를 작업 디렉터리로 사용하는 실행 중인 HTTP 서버를 찾아 재사용합니다. 특정 포트가 응답한다는 이유만으로 다른 프로젝트를 연결하지 않습니다. 실행 중인 서버가 없으면 Vite 설정을 읽고 비어 있는 포트에 별도 개발 서버를 시작합니다. 프로젝트 소스와 Vite 설정 파일은 수정하지 않습니다. 현재 자동 시작은 Vite 프로젝트를 지원합니다.

Vite 의존성이 없으면 잠금 파일이 있는 프로젝트는 npm ci, 없는 프로젝트는 npm install을 실행합니다. 설치와 서버 준비 상태를 화면에 표시하고, 실패하면 실제 오류와 로그 및 다시 시도 버튼을 보여줍니다. backend 전용 프로젝트나 지원하지 않는 프론트에는 다른 앱을 대신 표시하지 않습니다.

플랫폼이 시작한 개발 서버는 플랫폼 종료 시 종료합니다. 기존에 사용자가 실행한 서버는 종료하지 않습니다. 로그는 `platform/state/previews/`에 저장합니다. 폴더 선택은 운영체제 다이얼로그를 사용하므로 현재 macOS에서 지원합니다.

## 코드 변경

새 모델 실행부터 수정 직전 원본과 검사 후 반영된 결과를 실행별로 저장합니다. 개요와 실행 상세에서 추가·수정·삭제 파일, 추가·삭제 줄 수를 확인하고 파일을 눌러 Monaco diff 편집기를 엽니다. 기본은 한 화면 비교이며 나란히 비교도 지원합니다. 편집기는 읽기 전용이고 본문은 파일을 선택할 때 조회합니다. 실패 후 복원된 후보는 반영된 변경으로 표시하지 않습니다. 나중에 프로젝트 파일이 바뀌어도 과거 실행의 비교는 바뀌지 않습니다. 원본을 저장하지 않은 기존 실행에는 비교를 만들어내지 않습니다.

개요의 마지막 실행 결과는 최근 모델 작업 하나를 기준으로 합니다. 성공이면 해당 실행의 diff를 바로 열고, 실패면 해당 실행의 실패 사유를 조회합니다. 실행 중·중지·기록 없음도 구분하며, 이전 실패를 대신 보여주지 않습니다.

통합 검증: `node platform/tests/workspaces-browser.cjs`. 임시 서버와 프로젝트에서 폴더 선택 API(선택·취소 응답 대체), 등록·전환·기록 분리·모델 요청·diff·실제 Vite 자동 미리보기를 확인하고 종료 시 제거합니다. 사용자 프로젝트를 수정하거나 모델 작업을 시작하지 않습니다.

재고 API는 http://127.0.0.1:8083 에서 `mdi-local-api` 컨테이너로 실행합니다. 프론트의 `/api` 요청은 이 주소로 전달합니다. 컨테이너를 다시 켤 때는 `docker start mdi-local-api`를 사용합니다. 앱 DB는 `mdi_local`, 테스트 DB는 `mdi_local_test`이며 백엔드 검사는 내부 Docker 네트워크에서 실행합니다.

처음 실행할 때 플랫폼 웹 의존성을 설치하고 빌드합니다. 앱 개발 서버가 꺼져 있으면 함께 시작합니다. 이 스크립트가 시작한 앱 서버는 플랫폼 종료 시 함께 종료합니다. 이미 켜져 있던 서버는 유지합니다. MLX와 PostgreSQL/Docker는 기존 로컬 서비스를 사용합니다.

## 실제 실행 경로

- `server.py`: loopback HTTP 서버, 실행 프로세스 관리, 파일 해시를 통한 검사 유효성 확인.
- `adapter.py`: `local-only/harness/harness.py`를 불러와 모델·도구·검사 이벤트를 기록합니다. 기존 하네스의 도구를 사용하고, 로컬 모델이 작성한 `local-only/harness/supervisor.py`의 실행 루프를 연결합니다.
- `checks.py`: 모델을 부르지 않고 기존 빌드·브라우저·백엔드 검사 또는 하네스 자체 검사를 실행합니다.
- `web/`: Astryx 화면과 실제 검사 소요 시간을 그리는 ECharts 차트.

코드 생성·수정은 로컬 Gemma가 수행합니다. 모델 주소는 `127.0.0.1:8099/v1`, 모델은 `mlx-community/gemma-4-26B-A4B-it-OptiQ-4bit`입니다. Ponytail 스킬은 `~/.local/share/mlx-server/skills/ponytail/SKILL.md`에서 읽습니다. MLX 환경도 `~/.local/share/mlx-server`에 있습니다.

`local-only/` 프로젝트·하네스는 로컬 모델이 작성했고, 이 `platform/`은 사용자 요청에 따라 Codex가 작성했습니다. 플랫폼 소스를 모델이 작성한 것으로 표시하지 않습니다.

## 상태 읽기

프로젝트 소스에는 frontend/src와 backend/src만 표시하며 하네스는 제외합니다. 파일 트리와 파일 탭, 줄 번호·구문 강조·접기·파일 내 검색이 있는 읽기 전용 편집기로 표시합니다. 편집기는 소스 화면을 처음 열 때 불러오고 작업자·언어 파일도 로컬에서 제공합니다. 파일을 전환할 때 스크롤과 커서 위치를 유지합니다. 탐색기 너비와 줄바꿈을 조절할 수 있습니다.

실행 기록은 최근 20개부터 표시하고 스크롤로 다음 페이지를 읽습니다. 이벤트는 80개씩 읽으며 필터도 서버에서 적용합니다. 목록은 가상 스크롤로 화면 밖 행을 렌더링하지 않습니다. 검사 출력과 모델 응답 본문은 펼칠 때 요청합니다. `/api/state`에는 최근 기록만 포함하고, JSONL 위치를 SQLite에 색인해 새로 추가된 부분만 반영합니다. `history.sqlite3`는 파생 색인이며 원본 실행 기록은 각 실행 폴더의 JSONL입니다. 첫 시작의 색인 구성과 프로젝트 파일 해시 계산은 별도로 수행됩니다.

선택한 모델 실행에 흐름도를 표시합니다. 기본 순서는 위에서 아래로 읽고, 검사 실패 후 복원·재시도는 오른쪽 분기로 표시합니다. 현재 위치와 방문 경로는 실행 이벤트를 따라 갱신됩니다. 단계를 누르면 파일 경로와 검사·오류 근거를 볼 수 있고, 선택 해제로 상세를 닫을 수 있습니다. 검사만 실행한 기록에는 흐름도를 표시하지 않습니다. 종료된 실행에는 진행 중 표시를 남기지 않습니다.

검사는 모델 작업의 완료 확인 과정에서만 실행합니다. 검사 전용 버튼과 전체 검사 버튼은 없으며 HTTP 실행 API도 모델 작업만 받습니다. 내부 유지보수용 검사 CLI와 기존 검사 기록은 보존합니다.

MLX 연결됨은 모델 서버 연결 상태입니다. 실제 추론 중인지는 실행 상태와 모델 요청/응답 이벤트로 확인합니다. 실행 중지는 플랫폼이 시작한 프로세스에만 적용합니다. MLX 서버 자체를 종료하지 않으며, 이미 접수한 추론이 즉시 취소됐다는 보장은 하지 않습니다.

로컬 모델이 요청을 최대 4단계로 나눕니다. 파일을 수정하면 선택한 검사를 실행하고, 실패한 수정은 해당 회차 이전의 파일로 복원합니다. 검사를 통과해 반영한 앞 단계의 수정은 유지합니다. 기존 Java 테스트의 기대값 변경과 테스트 삭제를 막습니다. 읽기만 한 회차에는 검사를 반복하지 않습니다. 오류 출력과 현재 파일을 바탕으로 선택한 최대 회차 안에서 재시도하며, 한도가 끝나면 실패로 종료합니다. 사용자의 동시 수정과 충돌하면 덮어쓰지 않고 중단합니다. 정상적인 중지 신호에는 미검증 수정을 복원하지만, 강제 종료나 전원 손실 이후의 자동 복구는 아직 지원하지 않습니다. 플랫폼을 끈 동안 계속 감독하거나 무제한 자동 재시작하지는 않습니다. 재시작 시 종료 여부를 확인할 수 없는 실행은 별도 상태로 표시하고, 살아 있는 외부 실행이 있으면 중복 실행을 막습니다.

실패한 후보의 차이와 원인은 `local-only/harness/state/failures.json`에 보관합니다. 같은 소스·의존성 상태에서 이미 실패한 변경을 재사용하거나, 정상 동작하던 Java import를 다시 제거하면 실행 전에 차단합니다. 코드나 의존성이 바뀌면 해당 제약을 적용하지 않습니다. 재시도에는 복원 후 현재 파일을 전달하며, 파일을 이미 전달한 상태에서 디렉터리 탐색만 반복하면 해당 탐색 도구를 잠시 제외합니다.

기존 줄을 유지하는 `insert_text`, 여러 위치에 추가하는 `apply_insertions`, 여러 짧은 구간을 교체하는 `apply_edits`를 제공합니다. import와 JSX처럼 함께 바뀌어야 하는 수정은 한 트랜잭션에서 검사합니다. 추가 도구는 5,000자, 교체 도구는 6,000자 이하 파일을 대상으로 합니다. UI 작업에는 현재 App.tsx와 실제 Astryx Button 문서를 먼저 제공합니다. 새 폴더 발견도 진전으로 계산하고, 이미 탐색한 목록을 새 문맥에도 유지합니다. 한글 도구 응답은 Unicode 이스케이프 없이 전달합니다.

백엔드 작업에는 로컬 Maven 캐시에서 확인한 Spring 테스트 API 경로와 실제 SQL 리소스 목록을 전달합니다. 테스트 실패는 실행 직후 생성된 Surefire XML의 실패 메시지를 우선 읽습니다. 정상적인 입력 검증 경고가 실제 실패 원인을 가리지 않도록 했습니다. 같은 수정 도구가 동일한 오류를 반복하면 해당 단계에서 다른 도구로 전환합니다.

복원 뒤에는 현재 소스의 검사 결과와 버린 수정안의 오류를 구분해 전달합니다. 요청에 명시한 파일을 문맥에 먼저 넣습니다. Spring 테스트 격리는 `isolate_spring_test`로 트랜잭션 복원과 범위를 지정한 테스트 데이터 정리를 함께 추가할 수 있습니다. SQL 문자열 처리는 도구가 맡고, 테스트 기대값과 기존 본문은 유지합니다.

실제 프로젝트 파일과 Controller 소스를 문맥에 전달합니다. 없는 파일을 읽으면 실제 일치 경로를 알려주고, 복원으로 삭제된 새 파일의 실패 기록도 유지합니다. 별도 화면을 요청한 작업은 새 화면 파일과 메뉴 등록에 필요한 meta·default export가 있어야 완료할 수 있습니다. 동일한 파일 내용의 재작성은 수정으로 계산하거나 복원하지 않습니다.

CLI 기본 실행도 같은 루프를 사용합니다. 기존 `--demo`는 호환성을 위해 예전 데모를 유지합니다.

```sh
python3 local-only/harness/harness.py "작업 내용" --workspace local-only --check 'frontend|framework' --max-rounds 16
```

현재 자동화 범위는 프로젝트 파일 수정과 등록된 검사입니다. 패키지 설치·배포·임의 터미널 명령까지 실행하는 범용 에이전트는 아닙니다.

실행별 요청·상태·원문 출력·구조화 이벤트는 `platform/state/<id>/`에 저장됩니다. 이 폴더와 웹 빌드·의존성은 Git에서 제외합니다. 이전 `STATUS.json`의 실행 중 표시는 사용하지 않습니다.

## 검증

```sh
python3 -m unittest discover -s platform/tests -v
npm --prefix platform/web run build
cd platform/web && npx astryx doctor --built .
```

브라우저 통합 검사는 서버가 실행된 상태에서 `node platform/tests/browser.cjs`로 실행합니다. 기존 범용 Playwright 설치 경로를 사용하며 작업을 새로 시작하지 않습니다. 결과와 캡처는 `platform/state/evidence/`에 저장합니다.

API는 localhost에만 바인딩하며 실행 요청에 세션 토큰과 Origin 검사를 적용합니다. 소스는 읽기 전용이고 프로젝트 밖 경로·심볼릭 링크 탈출을 차단합니다.

흐름도 검증: `node --experimental-strip-types platform/tests/flow-state.mjs`, `node platform/tests/flow-browser.cjs`. 브라우저 검사는 실제 화면을 읽은 뒤 격리된 응답으로 재시도·중지·과거 기록을 확인하며 실행 요청은 보내지 않습니다.

추가 확인 명령: `node platform/tests/ide-browser.cjs`, `node platform/tests/history-browser.cjs`. 기록 검사는 실제 페이지 조회와 격리된 2,000개 이벤트 응답으로 페이지 크기·상세 지연 조회·렌더링 행 수를 확인합니다. `node platform/tests/item-registration.cjs`는 실제 API에 검증용 품목을 등록한 뒤 해당 품목만 제거하고 기존 데이터가 같은지 확인합니다.

새 파일의 검사 실패는 복원 후 원본 후보를 보관하고, 같은 모델에 오류 구간의 정확한 교체만 요청합니다. 수정 결과도 기존 파일 도구·체크포인트·검사를 통과해야 반영하며, 전체 호출 한도를 공유합니다.

실패한 실행에는 종료 이유, 모델 호출 수, 완료 단계, 오류 근거를 표시합니다. 이후 검사에서 해결된 오류는 이전 오류로 구분합니다. 기본 호출 한도는 32회이며 화면에서 최대 64회를 선택할 수 있습니다. 마지막 모델 호출에서 작업을 마친 경우에도 고정된 최종 검사는 수행합니다.

코드 검색은 `search_code` 도구로 제공합니다. `exact`는 zvec-grep의 `--rg`로 문자열을 찾고, `hybrid`는 키워드와 의미 검색을 함께 사용합니다. 검색 대상은 프로젝트의 frontend/src와 backend/src입니다. 의미 검색 전에 색인을 갱신하며, 결과의 실제 파일은 읽은 후 수정해야 합니다. 검색 실패는 도구 결과로 반환합니다.

검색 실행기는 `~/.local/share/mlx-server/search/node_modules/.bin/zg`이며 별도 ripgrep 설치 없이 패키지에 포함된 실행기를 사용합니다. 임베딩은 로컬 CPU 모델 `local/potion-multilingual-128m`, 모델 캐시는 같은 search 디렉터리의 models, 프로젝트 색인은 `local-only/.zvec-grep/`에 저장합니다. 최초 설치와 모델 다운로드에는 네트워크가 필요합니다. 검색에 원격 임베딩을 사용하지 않습니다. [zvec-grep 검색 문서](https://zvec.org/en/docs/zvec-grep/search/).

실패 표시 브라우저 검증: `node platform/tests/failure-browser.cjs`.

작업 실행 화면은 왼쪽 실행 기록과 오른쪽 실행 상세로 구성합니다. 상세 상단에 상태·시간·모델을 표시하고 로그, 변경 파일, 실행 흐름을 탭으로 전환합니다. 새 작업 입력은 상단 새 작업 버튼에서 엽니다. 개요에는 작업 시작 이동 버튼을 두지 않습니다.

실행 상태는 기록 목록·작업 단계·로그·흐름도에서 같은 배지로 표시합니다. 선택한 기록은 포커스 후에도 파란 배경을 유지하며 제목과 파일 경로는 줄바꿈합니다. 상단 도구 모음은 기본 40px이고, 페이지 제목을 중복해서 표시하지 않습니다. 로그는 시작·종료 이벤트를 한 줄로 합치며 오류 출력은 자동으로 펼칩니다. 화면 회귀 검사: `node platform/tests/ui-layout.cjs`.

모델 설정 메뉴에서 로컬 OpenAI 호환 API의 모델 ID·주소·표시 이름을 등록하고 수정·삭제할 수 있습니다. Temperature, 최대 출력 토큰, 응답 제한 시간을 저장하며 프로젝트 기본 모델을 지정할 수 있습니다. 연결 확인은 실제 짧은 응답을 요청합니다. 작업 중에는 연결 확인으로 모델을 바꾸지 못하도록 막습니다. 실행을 시작할 때 설정 사본을 기록하므로 이후 설정을 수정해도 과거 실행 정보는 유지됩니다. 등록 정보는 `platform/state/models.json`, 프로젝트별 기본값은 `projects.json`에 저장합니다. 확인: `node platform/tests/model-settings-browser.cjs`.

재고·자재·데이터의 예시 변경 요청에는 `update_seed_rows` 도구를 제공합니다. 모델이 기존 ID와 값·새 값을 지정하면 새 Flyway UPDATE 마이그레이션과 정확한 문자열 테스트 기대값을 함께 만들고, 기존 체크포인트로 한 번에 검사·복원합니다. 기존 마이그레이션과 행 ID를 보존합니다. 검사가 통과한 해당 단계는 하네스가 종료해 같은 변경을 반복하지 않습니다. 도구와 실행 정책 코드는 로컬 26B가 작성했고, 요청·응답과 조립 기록은 `local-only-evidence/autonomy`에 보관합니다.

새 화면에 meta/default 내보내기가 없으면 프레임워크 검사가 파일 경로와 필요한 내보내기를 먼저 보고합니다. 브라우저 JS 예외는 원래 stack을 보존하고 `BROWSER_RUNTIME_ERROR`로 모델 피드백에 우선 전달합니다. 등록 화면 작업에는 기존 등록 폼과 구현된 POST 컨트롤러를 소스 예제로 제공하며, 화면 작성 코드는 로컬 모델이 생성합니다. 검증: `node platform/tests/screen-runtime-browser.cjs`, `python3 -m unittest discover -s platform/tests -p 'test_screen_contract.py'`.

구버전 WebKit에서는 스크롤용 flex 컨테이너의 `overflow: clip` 카드가 내용 높이와 무관하게 축소돼 마지막 실행 결과가 제목 높이만 남는 문제가 있었습니다. 페이지 콘텐츠의 직접 자식은 줄어들지 않게 하고, 스크롤은 페이지 컨테이너가 담당하도록 지정했습니다. 교차 엔진 검사는 `node platform/tests/panel-browser.cjs`이며 Chromium·현재 WebKit·WebKit18에서 밝은/어두운 테마와 좁은/넓은 화면을 확인합니다. WebKit18 검사 설정은 `~/.local/share/mlx-server/browser-check/webkit18.json`을 사용합니다.

로컬 모델의 호출당 응답 제한은 기본 600초(10분)입니다. Gemma26B의 저장된 설정도 600초로 변경했습니다. 작업 전체의 시간 제한과는 별개입니다. 타임아웃이 발생하면 해당 응답의 도구를 실행하지 않고, 최근 관련 소스 최대 2개를 유지해 단계당 한 번만 재시도합니다. 호출 횟수 예산과 미확정 변경 보호, 사용자 중지 동작은 유지합니다. 연결 거절이나 잘못된 입력 등 다른 오류는 타임아웃으로 재시도하지 않습니다.

복합 요청은 완료 조건을 고정한 뒤 검증 가능한 작업으로 나눕니다. 각 작업은 담당 완료 조건, 수정할 파일, 선행 작업을 갖고 모든 완료 조건을 정확히 한 번 담당해야 합니다. DB 변경과 API는 함께 검증할 수 있는 기능 단위로 묶고, 화면 작업은 검증된 API 결과를 전달받습니다. 같은 모델이 의존 순서대로 실행하며 단계마다 새 대화를 사용합니다. 원래 요청과 계약 해시는 유지하고 해당 파일과 선행 단계의 실제 관측값만 전달합니다.

단계 검증은 담당 조건과 이미 통과한 앞 단계 조건을 함께 확인합니다. 단계 통과 이벤트는 전체 완료로 쓰지 않습니다. 마지막에는 원래 선택한 검사와 전체 완료 조건을 다시 실행하며, 실패한 조건의 담당 단계부터 뒤 단계를 재검증합니다. 이 라우팅과 코드·HTTP·브라우저 검사는 모델 호출 없이 수행합니다. 사용자 중지는 현재 단계의 미확정 수정만 복원하고 이미 검사된 이전 단계 변경을 보존합니다. 호출 예산은 모든 단계가 공유합니다.

실행 흐름의 작업 분할 계획에서 순서·선행 작업·완료 조건·수정 파일과 현재 단계를 확인합니다. `GET /api/jobs/<id>/strategy`는 최신 계획과 상태를 SQLite 색인으로 조회하므로 전체 로그를 다시 읽지 않습니다. 계획과 실제 검증 결과 인계는 실행의 검증 산출물 디렉터리에 저장합니다. 다른 실행에서 자동 재개하는 기능은 아직 없으며, 새 실행은 이미 충족된 조건을 실제 검사해 수정 없이 건너뛸 수 있습니다.

검증: `python3 -m unittest discover -s platform/tests -p 'test_divide*.py' -v`, `node platform/tests/strategy-ui-browser.cjs`. 모델 응답을 고정한 통합 검사는 실제 파일 수정과 실제 HTTP 응답으로 단계 전환·선행 기능 회귀·전체 검사 후 담당 단계 재개·사용자 중지를 확인합니다. 런타임 모듈의 로컬 모델 원문은 `local-only-evidence/autonomy`에 보관합니다.

계획 입력에는 완료 조건에서 계산한 항목별 허용 영역을 함께 보냅니다. API 검사가 없는 화면 요청은 계획용 백엔드 영역을 제공하지 않으며, 사용자가 선택한 백엔드 검사는 마지막 전체 검사에 그대로 남습니다. 완료 조건이 없는 불필요한 준비 단계는 제거하라는 구체적인 오류를 반환합니다. 자동 실행은 수동 승인 단계를 제공하지 않으므로 `manual` 초안은 계약 확정 전에 실행 가능한 조건으로 다시 작성하게 합니다. 계속 수동 확인만 제안하면 이유를 기록하고 종료하며 수정 반복으로 넘어가지 않습니다. 초안 반려 사유는 실행 로그의 ‘완료 조건 수정 필요’에서 확인합니다.

기존 화면의 AST 목록에는 소속 함수, 행 범위, 메타데이터·최상위 JSX·시작 태그 역할을 표시합니다. JSX 전체가 길이 제한을 넘어도 시작 태그는 먼저 수집하므로 스타일·속성 변경에 화면 전체를 다시 생성할 필요가 없습니다. JSX 조각 반환과 JSX 속성만 수정하는 범위를 별도로 검사합니다. 함수 안 삽입은 지역 선언·보조 함수만 허용하며 import/export·기본 화면 선언·최상위 return·중괄호 탈출을 적용 전에 거부합니다. after-imports 슬롯은 명명된 타입·보조 함수를 허용하되 기본 내보내기 중복을 막습니다. 원본 해시·중첩 범위 검사와 기존 체크포인트·빌드·Lint 검사는 유지합니다.

잘못된 AST 수정 피드백에는 같은 스냅샷의 실제 화면 수정 후보 ID를 함께 돌려주며, 수정 지침도 기본 프론트 모드에서 허용된 도구와 일치하도록 구성합니다. 분할 단계의 주 파일과 참조 파일이 겹치면 한 번만 문맥에 넣습니다. 실제 실패 호출 두 건을 재생한 결과와 로컬 모델이 1회 호출로 올바른 시작 태그를 선택한 기록은 `platform/state/evidence/ast-scope-repair/`에 저장합니다. 이는 AST 수정·복원 검증이며 원래 화면 요구사항 전체가 완료됐다는 뜻은 아닙니다.

요구사항 검토에는 실행 연산자(op/relation)와 사람이 읽는 공간 관계 설명(subject/assertion/reference)을 함께 전달합니다. 실제 연산자는 네이티브 파서가 이미 확인했으므로 모델은 설명 문구를 미정의 연산자로 오해해 반려하지 않고 요구사항 충족 여부를 검토합니다. 여러 요구 절이 같은 기하학적 관계를 공유하는 것 자체는 오류로 취급하지 않습니다. 실제로 반대 방향인 조건과 빠진 기능은 계속 반려하며, 승인 결과를 키워드로 무시하거나 자동 통과시키는 처리는 없습니다.

기본 프론트 작업의 모델 도구 목록에서는 기존 코드에 사용할 수 없는 edit_file/apply_edits/apply_insertions/insert_text와 백엔드 전용 변경 도구를 제거합니다. 새 파일과 workspace JSON의 write_file은 유지하되 기존 JS/TS 소스 경로를 금지 스키마에 명시합니다. 광고된 도구와 별개로 정규화된 실제 경로의 쓰기 제한은 유지하므로 도구명을 임의로 호출하거나 별칭 경로를 써도 기존 화면 전체를 덮어쓸 수 없습니다. 원래 선택한 검사와 호출 예산은 바꾸지 않으며, 명시적 diff/whole 형식과 백엔드 작업에는 기존 도구를 유지합니다.
